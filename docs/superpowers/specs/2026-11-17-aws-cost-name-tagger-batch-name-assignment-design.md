# AWS Cost Name Tagger — Batch Name Assignment Design (Draft)

- Date: 2026-11-17 (JST)
- Repository: `yohi/aws-cost-name-tagger`
- Source baseline: `9cf9718c5379347a285058a2f1d64c07df0576af`
- Status: **Draft for Human Owner adoption**. Committing this document does not approve Phase B, enable AWS writes, alter IAM, or lift Safety Hold.
- Scope: requirements and a minimal design proposal only. No implementation, test execution, credentials, or AWS operations are authorized by this document.

## 1. Purpose and success criteria

Use CUR-based cost discovery to identify chargeable AWS resources and assign a meaningful `Name` tag **as comprehensively as the supported APIs and least-privilege boundaries permit**, while preserving existing meaningful Name values.

Success requires:

1. Report the full CUR-recognized population **before** `--min-cost`, `--max-resources` and `--max-writes` limits, and the exact population evaluated at each later stage. Never describe a capped subset as fully covered.
2. Generate candidate Names using existing inference logic; skip non-generatable candidates and report them explicitly.
3. Require a separate, explicit Human Owner approval phase using the existing review CSV `approved=YES` convention.
4. Freeze and authenticate the **whole approved CSV** (target identity, Name, operation, approval decisions and other execution-relevant fields) before any changes; run only the approved entries.
5. Limit the AWS execution principal's *effective permissions* to the specifically authorized resource ARNs and the `Name` tag, on APIs that enforce that property.
6. Re-read Name immediately before mutation; never overwrite a Name containing a non-whitespace character.
7. Read back each attempted Name change and report verified, skipped, failed, and uncertain outcomes, with no automatic retry.

Completion means an auditable classification or explicitly reported **uninspected/unattempted** limit for every CUR-recognized resource in the declared input/month/account/`--kinds` scope. It does **not** mean every billing line is attributable to a resource or can receive a `Name` tag; capped or unverified portions must not be called complete.

## 2. Eligibility and scope

Reuse the current CUR import, service/resource identification, `--kinds`, `--min-cost`, and Name proposal implementation. Keep the existing default `--min-cost` value and the existing `--mode dryrun` behavior.

**F002 — Name state contract:** Use the same exact-case `Name` classification in CUR/metadata planning, review, Owner authentication and pre-send checks. Preserve the **raw** string without trimming:

| State | `name_key_present` | `name_raw_value` | Update eligible |
|---|---|---|---|
| `ABSENT` | `false` | JSON `null` (**key absent**, not present-null) | Yes |
| `EMPTY` | `true` | `""` | Yes |
| `WHITESPACE_ONLY` (**new**) | `true` | nonempty string for which `value.strip() == ""`, including spaces/full-width spaces/tabs | Yes |
| `NONEMPTY` | `true` | contains any non-whitespace character, e.g. `" web-prod "` | No; preserve |
| `UNKNOWN` | unverified | unverified | No; block |

A present-null/non-string Name value, case-variant/duplicate Name key, malformed tag state, ambiguous resource identity or failed read is **`UNKNOWN`**, never `ABSENT`. Bind the exact planned `(account, partition, region, resource_arn, proposal_id, name_state, name_key_present, name_raw_value, approved_name, aws_operation)` to the signed approval (§4). At pre-send, re-read Name and require **both** state **and raw value** equal the authenticated plan snapshot. Even `ABSENT → EMPTY` or one whitespace string changing to another is a **per-resource Fail-Closed skip**, not permission to replace it. `NONEMPTY` and `UNKNOWN` remain protected.

Where the inference engine cannot produce a Name, **do not ask for manual entry or write a tag**. Include the resource in a final `Name自動生成不可リソース一覧` with service, resource ID/ARN if known, billed cost, and the reason.

Resources below `--min-cost` are excluded from write consideration; report their count and total cost separately, so filtering is visible rather than mistaken for full coverage.

**F001 — Population accounting (disjoint set boundaries):** For the fixed CUR files, billing period, account, `--kinds` filter and the existing effective-cost metric, track: (a) CUR usage that cannot be attributed to a supported resource identity (`UNATTRIBUTABLE_CUR`, count and identifiable cost where possible); (b) **all** distinct identified costed resources **before truncation** (`CUR_RECOGNIZED`); (c) `BELOW_MIN_COST` versus `ABOVE_MIN_COST` within that recognized set; (d) selected top-ranked `--max-resources` candidates (`LOOKUP_SELECTED`) versus `MAX_RESOURCES_NOT_INSPECTED`; and, after metadata inspection and CSV approval, (e) approved rows attempted under `--max-writes` versus `MAX_WRITES_NOT_EXECUTED`. Name-generation failure, IAM/API unsupported, already named and not approved are **inspected-resource outcomes**, never substitutes for budget/cap exclusion classes.

Current `_cur_ranked_candidates()` truncates **after** threshold filtering (`--max-resources=100` by default), and `run --mode y` caps **interactive selection** (`--max-writes=20` by default) while still forbidding writes. A future batch executor must separately enforce an attempted-send cap without misreporting the historical interactive limit as execution. Calculate the disjoint set counts and cost totals from bounded **pre-truncation aggregates**, preserving original precision until report formatting; list identities/reasons when available. Preserve two-pass CUR receipt checks, resource/byte/row budgets, AWS read-call/time budgets and the current no-partial-candidate-report behavior on exhaustion. If accounting cannot be proven or a budget fails, no write may occur and the relevant coverage is `UNKNOWN/INCOMPLETE`, not zero. Reaching either limit means `coverage_complete=false` for the declared population, even when all inspected resources succeed.

**RV-02 — Candidate generation boundary (retained):** The future Batch-only entry injects `batch_name_state(tags) -> str` (the `state` projection of `classify_batch_name(tags) -> NameObservation`) and `candidate_states=("ABSENT", "EMPTY", "WHITESPACE_ONLY")` into the original `Investigator.resolve(item, *, name_state_fn=name_state, candidate_states=NAME_CANDIDATE_STATES)` decision points **before inference**. Its eligibility branches, final state and exception paths all use the injected classifier. The same metadata/lineage lookups, confidence and collision demotion produce the Batch `proposed_name`, evidence, status and untrimmed raw Name; a converted legacy `already_named` Plan cannot reconstruct or authorize it. Phase A keeps default `name_state()` and `NAME_CANDIDATE_STATES=("ABSENT","EMPTY")` with unchanged behavior.

**RV-04 — Original signed population contract (retained and refined by RG-B06):** A dedicated Batch Plan `schema_version=3` carries fixed CUR-input/period/account/kinds/threshold identity, `count`, selected `records`, and the mandatory versioned `cur_population` pre-cap summary. `cur_recognized = below_min_cost + above_min_cost` and `above_min_cost = lookup_selected + max_resources_not_inspected` hold for count **and exact costs**; `count=len(records)=lookup_selected.count`. `UNATTRIBUTABLE_CUR` counts billing rows, not distinct identifiable resources. The exact Plan bytes are authenticated by `BatchApprovalV1.plan_sha256` before CSV approval and later reporting. The legacy Phase A schema2 and capped candidate API are unchanged.

**RG-B06 — Exact CUR amounts without altering the Phase A float path:** The future Batch scanner performs the original bounded two-pass receipt-verified scan, but its **second pass** calculates two values for each recognized resource key: (1) the legacy `float` total used **only** to reproduce the original `_cur_ranked_candidates()` threshold (`--min-cost` as legacy float), stable ordering, tie order and `--max-resources` selection, and (2) an *independent* exact base-10 aggregate `Decimal` obtained directly from the selected **original CUR monetary string** using the same `Usage -> line_item_unblended_cost`, `DiscountedUsage -> reservation_effective_cost`, `SavingsPlanCoveredUsage -> savings_plan_savings_plan_effective_cost` rule as `cost_of()`. Do **not** convert any float back to Decimal or use its repr as evidence. Parse monetary fields as finite, valid decimal strings and accumulate without rounding (an integer coefficient/scale accumulator, or a sufficiently widened Decimal context with `Inexact`/`Rounded` traps and a full precision bound based on row budgets); malformed, overflow or inexact sums reject the entire Batch Plan. The proposed `CurCostAggregate` is immutable with `legacy_rank_cost: float`, `exact_cost: Decimal`; `partition_cur_population(aggregates: Mapping[tuple[str,str,str], CurCostAggregate], *, min_cost: float, max_resources: int) -> CurPopulation` operates on legacy float membership/order but emits **exact Decimal** cost totals and canonical decimal strings. A tie or boundary change may not be hidden; preserve the original deterministic insertion order and compare selected keys to the legacy ranking. This is a **parallel Batch-only path**, not a change to the existing Phase A `cost_of`, `cur_candidates` or reports. Signed `cost_usd` fields may be **negative** when genuine selected CUR rows are negative; counts remain nonnegative. Canonical decimal strings contain no exponent, nonfinite value, redundant trailing zeroes or `-0`; no amount is rounded before serialization.

**RG-B06 — CUR selection taxonomy and Plan schema v2:** Preserve existing `_cur_selected_usage` period, account, charge-type and USD checks as the *declared monetary scope*; rows outside that scope are `OUT_OF_SCOPE` and never counted as `UNATTRIBUTABLE_CUR`. Within that scope, inspect kind eligibility before unresolved-resource accounting, in this order: (i) `OUTSIDE_REQUESTED_KINDS` when a **known supported kind** is excluded by `--kinds`; (ii) `UNSUPPORTED_KIND` if the CUR resource ID cannot resolve to a supported kind (keep separately even if a restrictive `--kinds` filter exists); (iii) `UNATTRIBUTABLE_CUR` for remaining in-scope supported-kind rows with **missing resource ID, missing required region, or malformed/mismatching resource identity**; (iv) `CUR_RECOGNIZED` for one exact `(kind,locator,region)` identity. A missing ID with no safely proven kind is `UNATTRIBUTABLE_CUR` with reason `MISSING_RESOURCE_ID`; a declared nonmatching account is excluded before classification, while an ARN account inconsistent with a selected account is `UNATTRIBUTABLE_CUR/IDENTITY_MISMATCH` and never a candidate. Do not merge excluded kinds or unsupported kinds into unidentifiable billing rows. Preserve aggregate monetary values and input-row counts per reason; do not pretend a billing-row count is a distinct resource count. An ambiguous row failing a safe classification or amount parse blocks `accounting_complete=true` and Plan publication.

To make the taxonomy explicit, **bump only the future `cur_population.schema_version` to `2`**, keeping the enclosing Batch Plan `schema_version=3` and Phase A schema2 intact. Required exact keys are `schema_version`, `accounting_complete`, `cur_recognized`, `below_min_cost`, `above_min_cost`, `lookup_selected`, `max_resources_not_inspected`, `unattributable_cur`, `outside_requested_kinds`, `unsupported_kind`. Each recognized-set value is `{count: int>=0,cost_usd: canonical signed decimal str}`; each of the three billing-line classes is `{billing_rows: int>=0|null, cost_usd: canonical signed decimal str|null, known: bool}` with null fields iff unknown. For an in-scope scan completed without ambiguity `known=true` (including genuine zero). These three classes are separate from recognized-resource conservation; recognized-set count/cost equalities from RV-04 remain exact. If any required in-scope cost is unknown/invalid, fail closed rather than assume zero or release a partial Plan. Record the declared CUR period/account/kind-filter and the legacy float-based selected identities to reconcile to the exact cost subtotals. Future Task 1 regression evidence includes decimal `0.1+0.2=0.3` preservation, negative amounts, near-threshold float ranking compatibility, known-kind filter exclusions, unsupported kind and missing-ID reasons, and exact Plan-to-Report sums.

**Review F003 — Signed Scope declaration and independent runtime evidence (Batch-only):** The frozen Batch Plan JSON `schema_version=3` has a mandatory top-level `scope_declarations` **array**. Each element has **exactly** `{writer_control_scope_id: nonempty string, account: 12-digit string, partition: string, region: nonempty string, resource_arns: nonempty sorted-lexicographic unique array of exact canonical ARN strings}`. Entries are sorted by `writer_control_scope_id`; IDs are unique, and an `(account, partition, region, resource_arn)` must not belong to more than one entry. The Plan author provides these declarations **before Plan serialization/CSV projection**, without copying runtime `ScopeEvidence` into the Plan; the Scope IDs are existing opaque `ScopeEvidence.writer_control_scope_id` identifiers, **not** newly derived hashes or claims of effective safety. The frozen Plan bytes, including declarations, contribute to signed `plan_sha256`.

For an `approved=YES` Plan row, `prepare_batch_approval` resolves its canonical `(account, partition, region, resource_arn)` from the immutable Plan record and the fixed kind/operation registry, matches **exactly one** declaration containing that exact ARN, and copies that declaration's exact `writer_control_scope_id` into the approved row tuple. This is the **only deterministic Scope-ID derivation**; never take `scope_id` from an editable CSV cell, a caller argument, a default, a live unverified Scope object or `Resource:"*"`. Missing/duplicate/overlapping declarations, wrong identity/ARN mapping or an unknown Scope ID block preparation and verification **before any Row Authority or Intent**. Recomputing the tuples from the same Plan/CSV must yield identical `approved_rows_sha256`.

At **every** row admission and Batch first-send consumption, independently reacquire and verify the protected runtime `ScopeEvidence` for that declared ID: exact `writer_control_scope_id`, account, partition, region, `resource_arn in controlled_arns`, validity window, responsible Owner, writer-evidence digest and current ledger Scope `CLEARED`, plus the separate per-target `SideEffectEvidence` and all Batch-wide covered-scope HOLD checks. Other independently controlled ARNs never become signed Batch targets. A Plan declaration is **only signed intended scope**, never proof that G1/G2, IAM, Trust or runtime scope is safe. Absent, stale, ambiguous or mismatching evidence returns `BLOCKED_SCOPE_MISMATCH` / `BLOCKED_WRITER_UNKNOWN` / `BLOCKED_SCOPE_STATE_UNKNOWN` as applicable, **zero Intent, zero Permit, zero send**, and Batch STOP/host Fail-Closed per §4; it cannot be converted to a successful Skip.

**Review F002 — Approved row eligibility at signing and verification (Batch-only):** Only a row whose immutable Plan `status` is **exactly** `"proposed"`, `confidence` is **exactly** `"high"` or `"medium"`, and exact-case Name observation is `ABSENT` (`name_key_present=false`, `name_raw_value=null`), `EMPTY` (`true`, `""`) or `WHITESPACE_ONLY` (`true`, nonempty string satisfying `value.strip()==""`) can have editable CSV `approved=YES`. The Plan must contain a unique nonempty `proposal_id`, valid canonical target ARN/account/partition/region and allowed operation, valid unambiguous inference evidence, and a nonempty generated `proposed_name` with `proposed_name == proposed_name.strip()`, no control characters, and service/kind-specific Name/tag-value validation. The **only** `approved_name` for this Batch is the **exact** immutable Plan `proposed_name`; the 14-column CSV has no editable Name override. It must be a meaningful value, never `""`, whitespace-only, malformed, unsupported, or caller substituted. Any Plan/CSV mismatch, invalid confidence/status/state/raw tuple, duplicate target, non-generatable/`already_named`/`manual_review`/`UNKNOWN`/API-error row bearing `approved=YES`, or invalid Name causes **whole draft/signature verification rejection**, even if a signature over that defective input exists: no `VerifiedBatchRowAuthority`, no Intent and no SDK send. Non-YES rows may be reported but never gain write authority. These Batch checks do **not** loosen Phase A `name_state()` or its single-ARN approval rules.

**DOC-REF version invariant:** The outer Batch Plan is `schema_version=3` and its mandatory CUR summary is `cur_population.schema_version=2`; neither this correction nor the signed Scope/Cap extensions change the original `BatchApprovalV1` payload schema or Phase A schema2.

## 3. Approaches considered

- **A — Single Owner approval for the reviewed CSV (selected):** use the existing per-row `approved=YES` decisions, then bind the full approved CSV content to one verifiable Owner approval. Simple operator experience for many resources while retaining immutable per-resource execution scope.
- **B — Separate Owner execution approval for every resource (not selected):** aligns with existing Phase A single-ARN authorization but adds excessive signing and review work when covering many chargeable resources.

The existing Phase A plan currently requires one ARN / Name / operation per authorization; **A is a deliberate proposed change to this contract, not a permission to bypass it**. Preserve existing fail-closed controls until the new authorization scope is explicitly adopted and implemented. **F003:** The single Owner signature authorizes one **fixed batch**; each approved row gains a separate **verifier-derived, single-use row authority** without a new Owner signature. The existing `VerifiedEnvelope(kind="execution")` may **not** be forged or interpreted as a batch approval.

## 4. End-to-end workflow

1. **Discover and propose:** extract above-threshold costed resources; read existing tag/metadata state; generate and classify candidate Names.
2. **Dry-run:** present all proposed changes and skipped/unsupported resources without any AWS mutation. Retain `run --mode dryrun`, and expose a clear `--dry-run` on the eventual batch execution path (not yet implemented).
3. **Review CSV:** retain the existing `.review.csv` columns `approved,proposal_id,kind,locator,region,effective_usage_cost_usd,status,name_state,name_key_present,name_raw_value,existing_name,confidence,proposed_name,evidence` and the exact `approved=YES` convention. **Only `approved` is editable.** The legacy CSV contains **no ARN, Account or AWS operation columns**; resolve those from the frozen Plan’s `scope_declarations` and exact service-operation mapping (runtime `ScopeEvidence` is verified independently later) for a verifiable Owner-visible batch manifest, not by trusting caller-supplied fields. All non-`approved` cells must match the known CSV projection of the Plan exactly.
4. **Owner sign-off:** choose **exact CSV bytes**, not alternative canonical CSV serialization: `csv_sha256 = SHA256(csv_bytes)` covers BOM, line endings, header, row order, approved and unapproved rows. Also bind `plan_sha256 = SHA256(original_plan_bytes)` and the canonical digest of resolved approved-row tuples. Sign the **canonical UTF-8 JSON** `BatchApprovalV1` specified below using a distinct OpenSSH signature namespace and the pre-enrolled `OwnerTrust`. An unsigned digest, CSV containing `approved=YES`, or a CLI flag is **not** authority.
5. **Preflight:** require the exact Plan/CSV bytes and signature again; parse CSV as strict UTF-8 with the **single expected UTF-8-SIG BOM** and the exact header/order; reject unknown/missing columns, duplicate headers, extra/missing/reordered rows, duplicate `proposal_id` or duplicate effective ARN/operation, unknown approval values, all unexpected edits and new targets. Each row must map to exactly one Plan record, with its original Name state/raw value and derived ARN/account/partition/region/operation. Verify actual STS principal/session policy, runtime scope and IAM effective-permission restrictions (§5). A changed CSV, Plan, signed row tuple, session identity or permission scope **rejects the batch before any Intent**.
6. **Execute sequentially:** for each strictly `approved=YES` row only, use the verifier-derived row authority below; acquire current state and require both its state **and exact raw Name value** still equal the signed Plan snapshot. Preserve durable per-row Intent/no-replay protection and consume at most one `FirstSendPermit` **before** the sole service-specific Name-only send. A changed Name is a per-resource no-send skip, even if its new state is also eligible. Do not auto retry or rollback; the **signed Plan `execution_limits.max_send_attempts`** caps durably consumed first-send attempts and separately classifies remaining approved rows (Review F001).
7. **Readback and report:** re-fetch Name and report `APPLIED_VERIFIED` only when it matches the signed approved value; otherwise mark failure/`OUTCOME_UNKNOWN` without re-send. Readback mismatch **persists writer-control scope `HOLD`**; inability to persist HOLD or establish the affected scope blocks the host. For simplicity, any `OUTCOME_UNKNOWN` or scope `HOLD` **stops the whole batch**, marking all remaining rows `NOT_ATTEMPTED_BATCH_STOP`. No automatic resumption or issuing a second row permit is allowed.

**RG-B09 — Explicit no-auth Preview -> Owner signature -> Authenticated Report flow:** The unsigned Batch Plan schema3 and its unchanged `.review.csv` are first validated structurally into `BatchDraft(plan_bytes, reviewed_csv_bytes, approved_rows, cur_population)`; this is **not** `VerifiedBatchApproval`, an Intent capability, or an AWS execution credential. `build_batch_dry_run(plan_bytes: bytes, csv_bytes: bytes, *, report: DraftBatchReportSink) -> DraftBatchReport` generates `authentication_state="UNSIGNED_PREVIEW"`, `execution_allowed=false`, the Owner-visible proposed ARN/Name/operation/row manifest, population/cost totals and no-send outcomes **before signature**. Neither this method nor `DraftBatchReportSink` may open/admit a Ledger Intent, consume a Permit, construct a write SDK client or mutate AWS. It is strictly local and does not assert Owner approval.

After the Owner edits **only** `approved` cells, `prepare_batch_approval(plan_bytes: bytes, csv_bytes: bytes, *, owner_principal_id: str, owner_key_fingerprint: str, authorized_role_arn: str, issued_at_utc: str, expires_at_utc: str, batch_nonce: str) -> PreparedBatchApproval` validates the same exact Plan/CSV projection and fixed approved row map, derives all authoritative ARNs/Name/API/scope from the Plan, computes `csv_sha256`, `plan_sha256`, `approved_rows_sha256` and constructs the **unsigned canonical** `BatchApprovalV1` JSON payload with signed `allowed_role="batch-approver"` plus its `batch_id`. It outputs `canonical_payload_bytes`, a signer-facing nonsecret request (OpenSSH Batch namespace) and an **Owner-visible** immutable manifest of rows, accounts, old/raw Names, approved values, operations, scope, costs, excluded/uninspected counts and all digests. All claimed Owner fields remain **untrusted** until the independently supplied detached OpenSSH signature is verified against current protected OwnerTrust; preparing a payload does not sign it and cannot authorize a send. The Owner signs those exact canonical bytes out of band; the exact envelope is `{payload,batch_id,signature_ref}`.

`verify_batch_approval(plan_bytes, csv_bytes, signed_batch_envelope, *, trust, now_utc) -> VerifiedBatchApproval` verifies signature and all exact digests and row identities, then keeps copies of **the original Plan/CSV bytes** bound to the frozen result. `make_authenticated_batch_report(batch: VerifiedBatchApproval, *, plan_bytes: bytes, csv_bytes: bytes, report: AuthenticatedBatchReportSink) -> AuthenticatedBatchReport` rechecks the original bytes/digests and returns `authentication_state="OWNER_VERIFIED"`, which is **not** an AWS write authorization without row/IAM/host/runtime gates. `execute_batch_offline` receives these exact bytes through its verified Batch inputs and only injected fake SDK clients, and its final `BatchRunResult` is rendered by the authenticated report sink; no unsigned Preview is silently promoted. CLI inputs and outputs: `prepare-batch --plan P --review C --owner-id ID --owner-fingerprint FP --role-arn ARN --issued-at UTC --expires-at UTC --nonce N --payload-out JSON --manifest-out JSON` (unsigned canonical payload and manifest only); `batch-dryrun --plan P --review C --report-out JSON` (unsigned preview only, **no signature required**); `verify-batch --plan P --review C --envelope E --report-out JSON` (signed Batch verification plus authenticated report only); and `batch-simulate --plan P --review C --envelope E --report-out JSON` (future, fake offline runtime only with isolated ledger fixtures). No CLI command provides an implicit real AWS send. Tests must prove the sequence `Plan -> unsigned Preview -> edited CSV -> canonical payload/manifest -> signature verification -> fake execution -> report` without cyclic authentication requirements; especially `test_unsigned_dryrun_never_opens_ledger_or_calls_sdk`, `test_prepare_payload_matches_signed_plan_manifest`, and `test_authenticated_report_rejects_foreign_plan_csv_bytes`.

The **only signed input** is `canonical_UTF8_JSON(BatchApprovalV1)` with deterministic recursive key ordering, no whitespace outside strings, `ensure_ascii=False`, no floats and no trailing newline, following the existing `name_tag_approval` canonical encoding. Neither the existing Phase A `verify_envelope(kind="name"|"execution")` nor its single-ARN `ExecutionAuthorization`/`VerifiedEnvelope(kind="execution")` is changed or repurposed.

Set `approved_rows_sha256=SHA256(canonical_UTF8_JSON(approved_tuples_in_CSV_order))` and compare to the signed field. - **F003 — Row admission and send consumption (future Batch ledger contract):** Derive each immutable `row_authority_id = SHA256(canonical_UTF8_JSON([batch_id, row_index, proposal_id, account, partition, region, resource_arn, approved_name, aws_operation, scope_id]))` (a typed JSON array; `row_index` is an integer) from the verifier-bound approved row; use `(batch_id, row_index)` and that exact operation identity as the unique durable Intent/replay keys. A `VerifiedBatchRowAuthority` from another `batch_id`, or an otherwise same-shaped row from a different signed Batch, cannot be substituted. Ledger lookup and first admission are protected by the existing cross-process lock and durable transaction; missing/torn history is `BLOCKED_SCOPE_STATE_UNKNOWN` (no optimistic new nonce/row registration). `OUTCOME_UNKNOWN`, Readback mismatch, scope/host `HOLD`, Owner key revocation/role change, expired Batch, or provenance/ledger loss blocks remaining rows. ## 7. Non-goals and residual risks

Do not create a new review UI, approval service, signing infrastructure, or broad IAM role. Do not reimplement Phase A. No manual Name entry for unsupported proposals, automatic retry, automatic rollback, or universal tag writing.
