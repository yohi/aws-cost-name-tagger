# AWS Cost Name Tagger — Batch Name Assignment Design (Draft)

- Date: 2026-11-17 (JST)
- Repository: `yohi/aws-cost-name-tagger`
- Source baseline: `9cf9718c5379347a285058a2f1d64c07df0576af`
- Status: **Draft for Human Owner adoption**. Committing this document does not approve Phase B, enable AWS writes, alter IAM, or lift Safety Hold.
- Scope: requirements and a minimal design proposal only. No implementation, test execution, credentials, or AWS operations are authorized by this document.

## 1. Purpose and success criteria

Use CUR-based cost discovery to identify chargeable AWS resources and assign a meaningful `Name` tag **as comprehensively as the supported APIs and least-privilege boundaries permit**, while preserving existing meaningful Name values.

Success requires:

1. Report the full CUR-recognized population **before** `--min-cost`, `--max-resources` and `--max-writes` limits, and the exact population evaluated at each later stage. Never describe a capped subset as fully covered.
2. Generate candidate Names using existing inference logic; skip non-generatable candidates and report them explicitly.
3. Require a separate, explicit Human Owner approval phase using the existing review CSV `approved=YES` convention.
4. Freeze and authenticate the **whole approved CSV** (target identity, Name, operation, approval decisions and other execution-relevant fields) before any changes; run only the approved entries.
5. Limit the AWS execution principal's *effective permissions* to the specifically authorized resource ARNs and the `Name` tag, on APIs that enforce that property.
6. Re-read Name immediately before mutation; never overwrite a Name containing a non-whitespace character.
7. Read back each attempted Name change and report verified, skipped, failed, and uncertain outcomes, with no automatic retry.

Completion means an auditable classification or explicitly reported **uninspected/unattempted** limit for every CUR-recognized resource in the declared input/month/account/`--kinds` scope. It does **not** mean every billing line is attributable to a resource or can receive a `Name` tag; capped or unverified portions must not be called complete.

## 2. Eligibility and scope

Reuse the current CUR import, service/resource identification, `--kinds`, `--min-cost`, and Name proposal implementation. Keep the existing default `--min-cost` value and the existing `--mode dryrun` behavior.

**F002 — Name state contract:** Use the same exact-case `Name` classification in CUR/metadata planning, review, Owner authentication and pre-send checks. Preserve the **raw** string without trimming:

| State | `name_key_present` | `name_raw_value` | Update eligible |
|---|---|---|---|
| `ABSENT` | `false` | JSON `null` (**key absent**, not present-null) | Yes |
| `EMPTY` | `true` | `""` | Yes |
| `WHITESPACE_ONLY` (**new**) | `true` | nonempty string for which `value.strip() == ""`, including spaces/full-width spaces/tabs | Yes |
| `NONEMPTY` | `true` | contains any non-whitespace character, e.g. `" web-prod "` | No; preserve |
| `UNKNOWN` | unverified | unverified | No; block |

A present-null/non-string Name value, case-variant/duplicate Name key, malformed tag state, ambiguous resource identity or failed read is **`UNKNOWN`**, never `ABSENT`. Bind the exact planned `(account, partition, region, resource_arn, proposal_id, name_state, name_key_present, name_raw_value, approved_name, aws_operation)` to the signed approval (§4). At pre-send, re-read Name and require **both** state **and raw value** equal the authenticated plan snapshot. Even `ABSENT → EMPTY` or one whitespace string changing to another is a **per-resource Fail-Closed skip**, not permission to replace it. `NONEMPTY` and `UNKNOWN` remain protected.

Where the inference engine cannot produce a Name, **do not ask for manual entry or write a tag**. Include the resource in a final `Name自動生成不可リソース一覧` with service, resource ID/ARN if known, billed cost, and the reason.

Resources below `--min-cost` are excluded from write consideration; report their count and total cost separately, so filtering is visible rather than mistaken for full coverage.

**F001 — Population accounting (disjoint set boundaries):** For the fixed CUR files, billing period, account, `--kinds` filter and the existing effective-cost metric, track: (a) CUR usage that cannot be attributed to a supported resource identity (`UNATTRIBUTABLE_CUR`, count and identifiable cost where possible); (b) **all** distinct identified costed resources **before truncation** (`CUR_RECOGNIZED`); (c) `BELOW_MIN_COST` versus `ABOVE_MIN_COST` within that recognized set; (d) selected top-ranked `--max-resources` candidates (`LOOKUP_SELECTED`) versus `MAX_RESOURCES_NOT_INSPECTED`; and, after metadata inspection and CSV approval, (e) approved rows attempted under `--max-writes` versus `MAX_WRITES_NOT_EXECUTED`. Name-generation failure, IAM/API unsupported, already named and not approved are **inspected-resource outcomes**, never substitutes for budget/cap exclusion classes.

Current `_cur_ranked_candidates()` truncates **after** threshold filtering (`--max-resources=100` by default), and `run --mode y` caps **interactive selection** (`--max-writes=20` by default) while still forbidding writes. A future batch executor must separately enforce an attempted-send cap without misreporting the historical interactive limit as execution. Calculate the disjoint set counts and cost totals from bounded **pre-truncation aggregates**, preserving original precision until report formatting; list identities/reasons when available. Preserve two-pass CUR receipt checks, resource/byte/row budgets, AWS read-call/time budgets and the current no-partial-candidate-report behavior on exhaustion. If accounting cannot be proven or a budget fails, no write may occur and the relevant coverage is `UNKNOWN/INCOMPLETE`, not zero. Reaching either limit means `coverage_complete=false` for the declared population, even when all inspected resources succeed.

## 3. Approaches considered

- **A — Single Owner approval for the reviewed CSV (selected):** use the existing per-row `approved=YES` decisions, then bind the full approved CSV content to one verifiable Owner approval. Simple operator experience for many resources while retaining immutable per-resource execution scope.
- **B — Separate Owner execution approval for every resource (not selected):** aligns with existing Phase A single-ARN authorization but adds excessive signing and review work when covering many chargeable resources.

The existing Phase A plan currently requires one ARN / Name / operation per authorization; **A is a deliberate proposed change to this contract, not a permission to bypass it**. Preserve existing fail-closed controls until the new authorization scope is explicitly adopted and implemented. **F003:** The single Owner signature authorizes one **fixed batch**; each approved row gains a separate **verifier-derived, single-use row authority** without a new Owner signature. The existing `VerifiedEnvelope(kind="execution")` may **not** be forged or interpreted as a batch approval.

## 4. End-to-end workflow

1. **Discover and propose:** extract above-threshold costed resources; read existing tag/metadata state; generate and classify candidate Names.
2. **Dry-run:** present all proposed changes and skipped/unsupported resources without any AWS mutation. Retain `run --mode dryrun`, and expose a clear `--dry-run` on the eventual batch execution path (not yet implemented).
3. **Review CSV:** retain the existing `.review.csv` columns `approved,proposal_id,kind,locator,region,effective_usage_cost_usd,status,name_state,name_key_present,name_raw_value,existing_name,confidence,proposed_name,evidence` and the exact `approved=YES` convention. **Only `approved` is editable.** The legacy CSV contains **no ARN, Account or AWS operation columns**; resolve those from the frozen Plan, signed scope evidence and exact service-operation mapping for a verifiable Owner-visible batch manifest, not by trusting caller-supplied fields. All non-`approved` cells must match the known CSV projection of the Plan exactly.
4. **Owner sign-off:** choose **exact CSV bytes**, not alternative canonical CSV serialization: `csv_sha256 = SHA256(csv_bytes)` covers BOM, line endings, header, row order, approved and unapproved rows. Also bind `plan_sha256 = SHA256(original_plan_bytes)` and the canonical digest of resolved approved-row tuples. Sign the **canonical UTF-8 JSON** `BatchApprovalV1` specified below using a distinct OpenSSH signature namespace and the pre-enrolled `OwnerTrust`. An unsigned digest, CSV containing `approved=YES`, or a CLI flag is **not** authority.
5. **Preflight:** require the exact Plan/CSV bytes and signature again; parse CSV as strict UTF-8 with the **single expected UTF-8-SIG BOM** and the exact header/order; reject unknown/missing columns, duplicate headers, extra/missing/reordered rows, duplicate `proposal_id` or duplicate effective ARN/operation, unknown approval values, all unexpected edits and new targets. Each row must map to exactly one Plan record, with its original Name state/raw value and derived ARN/account/partition/region/operation. Verify actual STS principal/session policy, runtime scope and IAM effective-permission restrictions (§5). A changed CSV, Plan, signed row tuple, session identity or permission scope **rejects the batch before any Intent**.
6. **Execute sequentially:** for each strictly `approved=YES` row only, use the verifier-derived row authority below; acquire current state and require both its state **and exact raw Name value** still equal the signed Plan snapshot. Preserve durable per-row Intent/no-replay protection and consume at most one `FirstSendPermit` **before** the sole service-specific Name-only send. A changed Name is a per-resource no-send skip, even if its new state is also eligible. Do not auto retry or rollback; `--max-writes` caps attempts and separately classifies remaining approved rows.
7. **Readback and report:** re-fetch Name and report `APPLIED_VERIFIED` only when it matches the signed approved value; otherwise mark failure/`OUTCOME_UNKNOWN` without re-send. Readback mismatch **persists writer-control scope `HOLD`**; inability to persist HOLD or establish the affected scope blocks the host. For simplicity, any `OUTCOME_UNKNOWN` or scope `HOLD` **stops the whole batch**, marking all remaining rows `NOT_ATTEMPTED_BATCH_STOP`. No automatic resumption or issuing a second row permit is allowed.

**F003 — Batch signature and per-row authority (future contracts only):**

- `BatchApprovalV1` is a strict JSON object with **exactly** `schema_version=1`, `purpose="aws-cost-name-tagger-batch-approval-v1"`, `csv_sha256`, `plan_sha256`, `approved_rows_sha256`, `account`, `partition`, `authorized_role_arn`, `owner_principal_id`, `owner_key_fingerprint`, `allowed_role`, `issued_at_utc`, `expires_at_utc` and `batch_nonce`. Fields other than `schema_version` are strings. Set the signed `allowed_role` to the **fixed Batch approval role** `batch-approver`; do not accept a role name selected by the executor or inferred solely from an untrusted envelope. Reject unknown/duplicate JSON keys, invalid types, noncanonical UTC timestamps, future issuance, expiry, invalid/replayed nonce and malformed digests. The **only signed input** is `canonical_UTF8_JSON(BatchApprovalV1)` with deterministic recursive key ordering, no whitespace outside strings, `ensure_ascii=False`, no floats and no trailing newline, following the existing `name_tag_approval` canonical encoding. Calculate `batch_id=SHA256(signed canonical payload bytes)`; verify an envelope containing exactly `payload`, `batch_id` and `signature_ref`, with the detached OpenSSH signature over those payload bytes under the **distinct** namespace `aws-cost-name-tagger-batch-approval-v1`. Do **not** accept `name`/`execution` signatures, self-declared signer keys, a digest alone or a CSV approval flag as an authorization.
- **F003 — Authenticated Owner principal/role, not self-attestation:** Reuse the existing host-protected `OwnerTrust` source (`allowed_signers` file, pinned SHA-256, trusted file owner/mode and protected Owner ID → public-key fingerprint → enrolled role/revocation map, as loaded by `name_tag_controlled._load_owner_trust()`). From this trusted map select the candidate keys for the **signed** `owner_principal_id`; cryptographically verify the signature under the Batch namespace; identify the **actual verifying public-key fingerprint**; and require byte/exact equality with the **signed** `owner_key_fingerprint`, enrollment for the same Owner ID, `revoked=false`, and enrolled role **exactly** `batch-approver` equal to signed `allowed_role`. The signature must not be accepted merely because its payload claims an Owner ID, fingerprint or role; a valid signature from another key/role is insufficient. At verification **and immediately before each row's ledger admission**, recheck the protected trust source and revocation/role, signature and payload/digest provenance, batch validity, and nonce/row replay state. Missing protected trust, inconsistent signer identity, unapproved role enrollment/namespace, stale/revoked key or inability to revalidate returns `BLOCKED_OWNER_AUTHN`, with **zero Intent and zero send**. Existing `OwnerTrust` key-enrollment/role/revocation administration is reused; any necessary Batch-namespace/role enrollment needs separate Human Owner approval. Neither the existing Phase A `verify_envelope(kind="name"|"execution")` nor its single-ARN `ExecutionAuthorization`/`VerifiedEnvelope(kind="execution")` is changed or repurposed.
- Resolve all reviewed CSV rows against exactly one original Plan record. For each `approved=YES` row, derive and validate the ordered typed tuple `(row_index, proposal_id, account, partition, region, resource_arn, name_state, name_key_present, name_raw_value, approved_name, aws_operation, writer_control_scope_id, approved="YES")` using the Plan and verified resource/scope/operation mappings—not editable CSV-derived ARN/API fields. Verify the exact original `Name` state/raw value and enforce a unique target across the batch. Set `approved_rows_sha256=SHA256(canonical_UTF8_JSON(approved_tuples_in_CSV_order))` and compare to the signed field. No approval is inferred for other rows; the full CSV still contributes to `csv_sha256`.
- Proposed future interfaces: `verify_batch_approval(plan_bytes, csv_bytes, signed_batch_envelope, *, trust: OwnerTrust, now_utc) -> VerifiedBatchApproval`; `derive_batch_row_authority(batch: VerifiedBatchApproval, row_index: int) -> VerifiedBatchRowAuthority`; and a **dedicated batch-aware ledger admission** `create_batch_intent(row_authority: VerifiedBatchRowAuthority, *, scope, side_effects) -> IntentHandle`. These types/methods are **not present in Phase A**. Only the trusted verifier may mint immutable `VerifiedBatchApproval`/row authority; the ledger must revalidate its original signature, signed digests, provenance, expiry, row membership and current scope before admitting a row. Do not counterfeit a Phase A `VerifiedEnvelope(kind="execution")` or bypass the existing ledger's signature gate.
- The ledger binds each durable Intent to the unique `(batch_id=SHA256(signed_payload_bytes), row_index, proposal_id, account, partition, region, resource_arn, approved_name, aws_operation, scope_id)` and rejects prior use of the same row identity or same operation authorization across process restarts. Preserve current exclusive-writer ownership, `CURRENT_EXECUTION_INTENT` versus `PRIOR_INCOMPLETE_INTENT`, persistent consumed nonces/IDs and **durable `SEND_ATTEMPT_CONSUMED` before the single call**. After crash, SDK timeout, missing Readback or outcome unknown, the consumed right is never restored. Existing scope `HOLD`/Owner `RELEASE` and host-wide Fail-Closed rules apply to the remaining rows, even when only some rows were attempted.

**Failure/return-code boundary:** For the future batch adapter, use existing fail-closed categories wherever applicable: bad Owner signature/CSV/Plan binding → `BLOCKED_OWNER_AUTHN`; untrusted/missing scope or ledger → `BLOCKED_SCOPE_STATE_UNKNOWN`; old/incomplete Intent → `BLOCKED_INCOMPLETE_INTENT`; replayed row/nonce → `BLOCKED_AUTH_REPLAY`; changed/unknown Name → `BLOCKED_NAME_UNKNOWN` (meaningful pre-existing Name → `BLOCKED_NAME_NONEMPTY`); unsupported write API → `WRITE_UNSUPPORTED`; unverifiable IAM scope → no send and `IAM制約による未対応`; uncertain send/Readback → `OUTCOME_UNKNOWN` and batch stop. Report classifications do not override the underlying Safety Hold or create new Phase A permissions.

A single CSV-level approval covers a **fixed set of individually constrained requests**, not unrestricted permissions to mutate future CUR discoveries or add rows after approval.

## 5. IAM least-privilege as a hard gate

**F004 — Selected IAM restriction scheme (future, not applied here):** Use a **dedicated AssumeRole execution role** with a fixed service/API-specific Name-only baseline, plus a **restrictive inline STS session policy** containing exact approved resource ARN(s) per batch (or disjoint approved sub-batch). Each session's write policy lists **only** its subset of signed approved ARNs and the supported tag-write API, with a condition restricting tag keys to `Name` (e.g. `aws:TagKeys`, only where genuinely enforced, with a present/non-null key set). Bind the verified batch ID, signed approved ARN subset, session-policy SHA-256, allowed actions, approved Name values, and verified STS role/session identity; require matching bounds **before every send**. This dynamic ARN restriction **reduces** the role's privileges; it must never be treated as a grant. Split a large batch into disjoint scoped sessions if STS policy limits are exceeded; stop if a safe subset policy cannot be supplied, rather than widening ARN patterns.

**F004 — STS issuance authority and credential provenance (future contract, not implemented):**

1. **Only issuer:** A trusted **host-only `BatchCredentialIssuer` inside the future Batch runtime**, not a new network service or approval UI, is permitted to request restricted temporary credentials. Its pre-enrolled bootstrap IAM principal is separately authorized for `sts:AssumeRole` on the **exact** dedicated execution `authorized_role_arn`, and is not allowed to write AWS Name tags directly. The role trust policy must limit who can assume it to this issuer principal; absence of proven issuer/role trust and permission boundaries means `AWS_WRITE_BLOCKED`. The ordinary executor cannot call STS to mint alternate credentials or substitute ambient profile/environment credentials. Issuer provisioning, trust-policy changes and AssumeRole calls require separate Owner authorization and are **not** performed by this document.
2. **Request construction:** The issuer accepts only a freshly revalidated `VerifiedBatchApproval`, an exact, disjoint subset of its authenticated approved ARN/Name/operation rows and a preverified API/tag-key allowlist. Derive a deterministic, minimal IAM policy JSON (UTF-8 canonical bytes) from that subset; it allows only the approved exact ARNs, approved write actions and the enforced `Name`-only condition, with no wildcard widening. Compute `session_policy_sha256=SHA256(exact Policy parameter bytes)` and `subset_sha256=SHA256(canonical approved row subset)`; bind both to `batch_id` and a unique immutable `subset_index` in a protected issuance context. Call **`sts:AssumeRole` only**, with `RoleArn` **exactly** the signed `authorized_role_arn`, `RoleSessionName="b-" + batch_id[:32] + "-" + six_digit_subset_index`, and the **exact inline `Policy` text**. Do not omit `Policy`, use `PolicyArns`, attach additional session grants/tags, enable credential-provider fallback or reuse a session for another batch/subset. Set `DurationSeconds` within STS/role limits and to expire no later than the signed Batch expiry; if a compliant session cannot be issued, block rather than widen the policy. Policy-size/packed-size errors fail closed, with no unconstrained fallback.
3. **Protected issuance receipt:** In the trusted issuer, bind **the actual submitted AssumeRole request** (bootstrap-principal identity, role ARN, session name, exact Policy bytes/hash, batch/subset IDs, ARN/action/Name restrictions, request ID) to **that same response** (`AssumedRoleUser.Arn`/`AssumedRoleId`, `Credentials.AccessKeyId`, `SecretAccessKey`, `SessionToken`, `Expiration`). Construct the scoped SDK client exclusively from that returned credential triplet and retain it together with an immutable, issuer-origin protected receipt (`IssuedBatchSession`) in the controlled host process. Check the assumed-role ARN/account/partition/role/session name and expiration against the fixed Batch and request; no caller-created receipt, copied `GetCallerIdentity` response or credential tuple from another session is valid. Protect the receipt/credential mapping and issuance event under the host's trusted UID/process boundary; redact secrets and tokens from logs. Do not persist raw secret credentials as ledger data. If the issuer crashes or issuance/receipt lineage is lost, no write and **no automatic credential reissuance/retry** for that subset.
4. **Send-time proof boundary:** `GetCallerIdentity` using the **issued** credentials may corroborate account and assumed-role session ARN, but **does not return or attest to the `Policy` supplied to AssumeRole**. Therefore the executor must verify the host-issued receipt, exact outgoing Policy digest/subset/approved-ARN binding, credential provenance and immutable client identity, valid expiration, signed Batch/Owner status, current row authority, ledger/Permit, and independently established effective IAM denial evidence **before each send**. Reject missing/mismatched issuance provenance, changed policy/ARN set, ambient/foreign/expired credentials, unsupported service controls, or unverifiable inherited/resource-based grants: `AWS_WRITE_BLOCKED` (or existing `BLOCKED_OWNER_AUTHN`/scope category when appropriate), **zero mutation calls**. STS's response is not a cryptographic proof of policy contents; the host receipt is valid only within the verified issuer/host trust boundary, not as standalone AWS proof. AWS IAM verification remains an unexecuted requirement; no live positive/negative access test or AssumeRole issuance is claimed here. AWS primary references: [STS AssumeRole request/response and session-policy limits](https://docs.aws.amazon.com/STS/latest/APIReference/API_AssumeRole.html) and [IAM session-policy/resource-based policy evaluation](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_evaluation-logic_policy-eval-denyallow.html).

Minimize read permissions to preflight/Readback. The effective write permissions must be restricted to the intersection of role baseline permissions and the session policy, subject to applicable permission boundaries, SCPs and explicit denies. Inspect **all** inherited policies, trust paths and any resource-based policy that may grant directly to an assumed-role session or otherwise bypass the intended session-policy restriction. A session policy or IAM simulator **alone** is not proof of an absolute deny. If a bypassing grant exists, cannot be ruled out, or an enforceable denial of off-batch ARN/non-`Name` mutations cannot be shown, fail closed. Never add create/delete/configuration rights or broad tag-set replacement rights for convenience.

For each service/resource kind, establish before enablement:

- the exact update API and exact resource-level ARN support;
- IAM tag-key conditions **actually enforced for that API**, with the requested key set present and exactly `Name` (e.g. service-supported `aws:TagKeys`, plus request-tag/value checks if required); do not assume support is uniform;
- whether the API performs key-scoped update or tag-set replacement;
- whether other tags and out-of-scope resources can be proven unmodifiable by the execution principal;
- a safe Readback mechanism.

**Fail closed on unsupported/unsafe services:** define an allowlist **per service/kind** of exact write API, supported resource-ARN granularity, Name-only tag-key condition, side-effect/tag-set preservation and Readback. EC2/EBS `ec2:CreateTags` is merely the **first candidate** to prove against exact volume ARN and applicable `aws:TagKeys`; it does not authorize other EC2 kinds or services. A tag-set replacement API, unsupported condition key, ARN wildcard requirement, policy bypass, unproven principal/CSV correspondence, or missing negative-denial evidence means **zero sends**. Report each such resource under `IAM制約による未対応` with count/cost and reason, not as Name-generation failure. Before enabling an API, confirm that an approved ARN/`Name` request matches the signed scope, while a foreign ARN, other tag key, alternate operation and unauthorized principal are denied. No IAM policy is created or applied by this document revision.

The desired coverage of existing supported kinds is a **discovery/reporting** target; write support is enabled per kind only where the least-privilege requirement holds.

## 6. Output and observability

Produce the normal proposal/report and a final run summary (CSV/JSON where the current reporting path supports it), identifying, for every relevant resource:

- cost, service/kind, ARN/resource ID, proposed Name and approval status (where available);
- `APPLIED_VERIFIED` after Readback, or a specific failure/`OUTCOME_UNKNOWN`;
- skipped: already meaningful Name, not approved, not eligible, invalid/unknown Name state;
- `Name自動生成不可` as a separately extractable list;
- unsupported IAM/service/API constraint and reason;
- excluded by `--min-cost` (at least count and total excluded cost);
- **F001 population accounting:** counts and **cost totals** for `CUR_RECOGNIZED`, `UNATTRIBUTABLE_CUR` (where attributable), `BELOW_MIN_COST`, `ABOVE_MIN_COST`, `LOOKUP_SELECTED`, `MAX_RESOURCES_NOT_INSPECTED`, `MAX_WRITES_NOT_EXECUTED` and the attempted-write set; metadata lookups not performed due to budget exhaustion are separately marked `READ_BUDGET_INCOMPLETE`;
- **F001 distinct outcomes:** the count/cost of inspected resources that are already named, unsupported by API/IAM, not approved, unable to generate Name, state unknown, Name changed after approval, send attempted, Readback verified, failed, outcome unknown or batch-stopped. Assign **exactly one primary final class** to each recognized above-threshold resource (with subordinate detail fields if needed), so category totals reconcile without double counting;
- `coverage_complete` and denominator: true **only** if every in-scope above-threshold CUR-recognized resource was investigated/classified with no cap, unknown population or budget gap; `writes_complete` is separate and never implied by dry-run, approval, or count of inspected candidates. Report each incomplete population and cost rather than silently discarding it.

Do not label an unattempted write successful, and do not silently drop excluded/unsupported resources. If accurate pre-cap counts/cost are unavailable, report `UNKNOWN/INCOMPLETE`, never `0` or comprehensive coverage.

## 7. Non-goals and residual risks

Do not create a new review UI, approval service, signing infrastructure, or broad IAM role. Do not reimplement Phase A. No manual Name entry for unsupported proposals, automatic retry, automatic rollback, or universal tag writing.

A pre-write Name check plus a subsequent update is **not an atomic compare-and-set** for services such as EC2 CreateTags. Competing writers or automation can alter Name between those steps. The existing G1 atomic-write norm therefore requires an explicit, narrowly scoped Human Owner decision before any real write path is enabled. The existing Phase A **INV-N05 one-ARN/one-Name/one-operation signed execution contract** also remains authoritative until Human Owner explicitly adopts this batch design and permits its normative change. Derived row authority is **not executable** by the existing CLI/executor/ledger. Keep ledger and fail-closed behavior where relevant; do not automatically add new infrastructure or review loops.

## 8. Implementation boundary / Owner checkpoint

Current Phase A artifacts (approval verification, scope checks, ledger, fake execution, candidate generation and read-only reports) remain reusable. The current production `execute-approved` and EC2 adapter write methods remain blocked.

**Existing Phase A versus proposed Batch contract (F002/F003/F004):** `aws_cost_name_tagger_v3.name_state()` currently classifies whitespace-only Name as `NONEMPTY`, while `proposal_key()` hashes the current state/raw value into the proposal identity; `name_tag_review._validate_review_state()`/`prepare_name_payload()` reject it, and `name_tag_execution.execute_once()` only accepts `ABSENT/EMPTY` and blocks production contexts. Existing `name_tag_approval.canonical_payload(kind="name"/"execution")` and `name_tag_ledger.create_intent(VerifiedEnvelope)` support **single-ARN signed executions only**. Therefore a future Batch implementation (separately approved) must change discovery/Plan+CSV projection, review validation, signed raw Name-state binding and pre-send re-read **together**, and add the purpose-separated Batch Owner/role verifier and batch-aware ledger admission of §4, plus the controlled **host-only** AssumeRole issuer, immutable session provenance and negative-denial checks of §5. These **proposed** `BatchApprovalV1`, `VerifiedBatchApproval`, `VerifiedBatchRowAuthority`, `BatchCredentialIssuer` and `IssuedBatchSession` are **not Phase A interfaces or implemented capabilities**. Merely loosening a Name condition, trusting a claimed signer role, treating GetCallerIdentity as session-policy evidence or passing a forged `VerifiedEnvelope` is forbidden. The existing Phase A Implementation Plan, `ExecutionAuthorization`, `OwnerTrust` behavior and live-write Hold remain **unchanged**.

**F001–F004 offline acceptance evidence (future only, no execution now):** Test count/cost conservation across pre-cap sets and both limits (including CUR/read budget fail-closed); all Name states, raw-value changes and UNKNOWN/malformed denial; full-CSV/Plan/signature/digest/row-mapping tampering, duplicates, replay, crash, durable one-shot consumption and HOLD stopping later rows; and positive/negative IAM-policy checks for approved ARN/Name versus foreign ARN, other key, alternate API, wrong principal and resource-policy bypass. These are future acceptance requirements, **not** test/CI authorization for this correction.

**Stop at this design document.** Subsequent work, only with explicit Human Owner approval, should cover the smallest implementation delta for CSV-level authorization, per-service least-privilege filtering, batch processing, `--dry-run`, and Readback/reporting. Create **no** Batch Implementation Plan here. Owner must independently decide (1) adoption of this Design and any INV-N05 change; (2) Trust Anchor/namespace enrollment and a G1 exception; (3) Phase B implementation/IAM changes; and (4) any real AWS runtime operation. Until then the older Phase A plan remains normative and all Safety Holds remain in force.
